## 经验

1. 适配器协议必须两边同步。
   - 主程序新增 `EbAdapterClient` 调用时，适配器 `AdapterProgram.cs` 必须同时支持同名 operation。
   - operation 名字大小写和拼写要完全一致，否则主程序会收到“未知操作”一类错误。
   - 新增请求或响应模型时，主程序 `Models.cs` 和适配器底部的 DataContract 模型要同步。

2. 权限配置写入要坚持“预览、确认、执行、读回、日志”。
   - 权限配置是高影响写入，不能只靠按钮直接执行。
   - 执行前要展示选中的用户、用户组和权限目录。
   - 执行后要区分新增、已存在跳过、失败。
   - 写入后必须读回确认，不能只相信 API 调用没有抛异常。

3. EB COM 能力边界不能靠猜。
   - 之前遇到 `COMException: HRESULT: 0x80046951` 时，直接猜 API 容易浪费时间。
   - 更可靠的路线是先找出真实调用点和对象类型，再决定是否需要改适配器协议或受控实测。
   - 主程序仍应避免 `dynamic`，把 EB COM 调用收敛在版本化 x86 适配器里。

4. 本地授权只能提高门槛，不能真正保密。
   - 如果程序需要离线自校验，校验逻辑和校验材料最终都在打包程序里。
   - 即使源码不给用户，反编译、调试、补丁修改仍可能绕过本地授权。
   - 真正强约束通常需要服务端校验、账号体系、在线授权或硬件绑定等配套。
   - 本项目当前已决定移除授权功能，因此后续不要继续维护 `.ealic`、隐藏入口或授权管理器代码。

5. 项目内资源要随程序输出一起管理。
   - 模板、帮助文档和版本信息不应依赖开发者本机路径。
   - 应放在项目目录下，并在 `.csproj` 中声明复制到输出目录。
   - 未来打包时只需要确认输出目录中的 `Templates` 被包含。

6. `NU1510` 不一定是错误。
   - 它通常表示包引用冗余。
   - 处理方式不是压制警告，而是先验证移除后是否仍能构建和运行。
   - 本次移除 `System.Text.Encoding.CodePages` 后完整构建通过，因此保留删除是更干净的做法。

## 教训

1. 不要让临时方案快速变成产品能力。
   - 授权管理器原本是为了隐藏给普通用户，但需求变化后如果不及时删除，会增加维护成本和误判风险。
   - 最终删除时需要同步清理源码、测试、项目引用和启动逻辑。

2. 调试要先缩小证据范围。
   - 真实 EB/COM 问题不适合一上来大面积试错。
   - 应先确认：主程序调用的 operation、适配器是否收到、COM 对象类型是否正确、读回路径是否可靠。

3. 文档和代码状态要一致。
   - 如果中途做过某项能力但最终删除，复盘文档必须写清“曾实现，最终移除”。
   - 否则后续开发者会误以为当前程序仍有该能力。

4. PowerShell 输出里的中文可能出现乱码，不等于文件一定损坏。
   - 本项目已有中文文档在 PowerShell 读取时可能显示 mojibake。
   - 修改中文文件时应避免用可能改变编码的 PowerShell 文本管道整文件重写。
   - 新增中文文档优先使用 UTF-8，并通过构建或源码读取验证实际使用不受影响。
